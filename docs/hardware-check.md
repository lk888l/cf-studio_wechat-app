# COM3 蓝牙串口模块实测

日期：2026-09-08。用户提供连接：USB CH343 → 蓝牙串口模块，Windows 端口 `COM3`。

## 实测结果

| 项目           | 结果                                   |
| -------------- | -------------------------------------- |
| 串口打开       | 成功                                   |
| 实际通信设置   | **9600 baud，8N1，无流控**             |
| DTR / RTS      | 均未使能                               |
| 模块版本回包   | `+VERSION=JDY-31-V1.35,Bluetooth V3.0` |
| 模块名称回包   | `+NAME=JDY-31-SPP`                     |
| 波特率参数回包 | `+BAUD=4`                              |
| 结束状态       | 串口已关闭并释放                       |

实物通过查询自报为 **JDY-31，固件 V1.35，Bluetooth V3.0，名称 JDY-31-SPP**，与最初描述的 HC-05 不同。实际 9600 baud 已连续正确收到三条 ASCII 回包，无需用其他波特率继续试探。`BAUD=4` 是设备原始参数代码；9600 的判定同时有实际成功串口通信支持。

车端固件 USART1 配置为 115200 baud，因此此模块**当前 UART 设置与已审计车端配置不匹配**。需要在接车前将模块设置或固件配置对齐。本轮只验证查询，没有修改该设置。

这次结果证明 USB 串口能与模块 AT 接口通信；没有验证手机蓝牙连接、BLE GATT 服务、数据透传、车端命令接收或机器人运动。型号与手册的蓝牙能力对照由项目的兼容性说明记录。

## 执行流程

1. 使用 PowerShell / `System.IO.Ports.SerialPort` 列举可见端口，确认存在 COM3；未打开其他端口。
2. 使用 9600 8N1 打开 COM3，DTR、RTS 均为 false，被动等待读取 1500 ms，没有收到已有数据；关闭并释放。
3. 以同样设置重新打开 COM3，依次发送下列三个查询，各等待 900 ms，再读取已到达的原始字节。
4. 在 `finally` 中关闭并释放串口。没有设置参数，没有发送运动或模块重启命令。

系统设备名称的辅助 `Get-CimInstance Win32_PnPEntity` 查询被 Windows 拒绝访问；此限制没有影响 COM3 串口实际打开和收发。CH343 名称来自用户给定接线说明，本轮未通过 CIM 独立复核 USB 芯片。

## 原始收发

以下 `\r\n` 是实际回车、换行字节的显示转义。

### 被动读取

```text
PORT: COM3
9600 8N1, Handshake=None, DTR=false, RTS=false
WAIT: 1500 ms
RX_TEXT: ""
RX_HEX: <empty>
```

### 版本查询

```text
TX_TEXT: "AT+VERSION\r\n"
TX_HEX: 41 54 2B 56 45 52 53 49 4F 4E 0D 0A

RX_HEX: 2B 56 45 52 53 49 4F 4E 3D 4A 44 59 2D 33 31 2D 56 31 2E 33 35 2C 42 6C 75 65 74 6F 6F 74 68 20 56 33 2E 30 0D 0A
```

```text
TX_TEXT: "AT+NAME\r\n"
```

## 后续硬件验收边界

- AT 参数匹配完成后，仍须验证所用手机端是否能使用模块的实际蓝牙传输协议；UART 查询成功不代表微信 BLE API 可以连接。
- 替换或桥接蓝牙模块后，应确认完整的紧凑 `R` 帧作为连续 UART 块送入 MCU；旧主分支不做跨块重组。
- 车上测试前依据 [固件协议审计](firmware-protocol.md) 检查 115200 8N1 和引脚，并先进行架空、低速及归零验收。
- 本轮没有覆盖失联停止；主分支中没有通信目标超时看门狗，不能以 AT 测试结果推断具备该保护。
