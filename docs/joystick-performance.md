# 小米手机摇杆画面卡顿优化（2026-11-05）

用户在小米安卓手机使用 WL1 遥控时反馈延迟和卡顿，并进一步确认主要是摇杆画面跟手不顺。本轮重点调整触摸到画面更新的路径，同时改善控制目标的发送调度。以下是代码检查和本地验证结果，尚未在用户手机上完成更新后的真机验收，没有测得可报告的帧率或端到端延迟。

## 找到的问题

- 原摇杆每次触摸移动都先进入逻辑层计算，再通过 `setData` 更新摇杆位置，画面需要等待一次视图层到逻辑层、再返回视图层的通信。
- 控制器每次状态更新都会将整份状态提交给页面；未按住的另一根摇杆也会重复提交归中位置。触摸、发送完成和接收回调会叠加产生页面更新。
- 每条 TX、RX、SIM 日志都会重新向视图层传送最多 60 条日志，即使用户正在遥控页、日志并不可见。
- 每次开始拖动都会重新异步测量摇杆布局，首次操作需要等待测量结果。连续移动时，还需要防止迟到的测量结果使用旧触点或恢复已经结束的手势。
- 原运动目标只随 100 ms 周期发送，变化后的输入需要等待下一次周期。这会增加控制链路的等待，但不能据此断定手机蓝牙本身的时延。

微信的 WXS 事件响应机制允许直接在视图层处理触摸，通过组件描述对象调整样式，并单向调用逻辑层方法；官方说明也将传统触摸经逻辑层再 `setData` 的往返通信列为交互延迟来源。[腾讯官方 WXS 事件响应文档](https://intl.cloud.tencent.com/ind/document/product/1219/61744)

## 本轮改动

| 路径           | 最终行为                                                                                                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 摇杆画面       | `joystick.wxs` 在 WebView 内处理触摸，直接用 `setStyle` 更新 `translate3d`；先绘制，再用 `callMethod` 将控制事件交给逻辑层。摇杆位置不再逐帧通过 `setData` 往返。                            |
| 双杆与松手     | 每根摇杆独立记住手指 ID；额外手指不接管。松手或触摸取消时，本地立即归中，再通知控制器按该杆语义归零。                                                                                        |
| 仪表与收发显示 | 普通控制目标、发送数和最近 RX 显示按 100 ms 窗口合并，约为 10 Hz；保留最新值，普通刷新等待上一轮渲染回调完成。启用、停止和握持状态变化及时更新。这个频率只用于仪表，不限制摇杆本地绘制频率。 |
| 日志           | 最近 60 条日志保存在逻辑层内存中，只在日志页可见时刷新列表。进入日志页会显示当前缓存；复制直接读取最新内存日志，清空同时清理缓存和显示。每条仍最多保留 256 字符。                            |
| 布局测量       | 页面准备完成、回到遥控页和尺寸变化后预先测量并缓存两杆位置。测量未完成就开始操作时仍接受触摸，结果返回后使用最新触点；手势或布局已经失效的旧回调不恢复操作。                                 |
| 控制目标发送   | 变化后的输入主动唤醒发送器，普通运动帧按至少 50 ms 的间隔合并，保留一份最新目标；握持不动时保留 100 ms 周期心跳。松手和停止绕过普通输入节流，但仍通过串行写入器发送。                        |
| BLE 与协议     | 保留写入成功回调后的至少 25 ms 空隙，main 命令仍为最多 20 字节、单次完整写入。保留串行发送、超时取消和会话隔离。                                                                             |

50 ms 是控制器的普通输入发送间隔设置，100 ms 是心跳周期设置，均不是蓝牙到车端实际执行的延迟承诺。链路繁忙时仍以串行写入完成为准，不重放历史触摸轨迹。当前模块 UART 为 9600 8N1，20 字节串口传输本身约需 20.8 ms，因此没有为了画面跟手而取消 BLE 帧间空隙或提高到触摸事件频率发送。模块和协议依据见 [ZX-D30 联调记录](zx-d30.md)。

## 已完成的验证

- WXS 模拟测试覆盖先绘制再转发、连续移动不丢最后目标、圆形限位、双杆及额外手指隔离、迟到布局、失效手势和触摸取消。
- 页面和控制器模拟测试覆盖刷新合并、日志缓存、触摸与生命周期清理、最新目标调度、松手停止优先等行为；模拟微信 API 不等同于真实安卓 BLE。
- 使用本机微信开发者工具 2.02.2608070 的原生 `wcc` / `wcsc` 编译器验证已接线的 WXML、WXS 和样式。WXS 使用受限 ES5 语法；模板检查需要将 `.wxs` 一并传入 `wcc`。
- 本轮未连接用户的小米手机测量，也未完成更新后的小车实测。最终画面体验与实际运动响应需要下面的真机步骤确认。

## 小米手机真机验收

1. **先用 SIM 检查画面。** 在同一部手机打开更新版，启用 SIM 和本地控制，分别及同时长时间拖动两杆，并反复快松、快按。观察摇杆是否持续跟手、松手立即归中，新的拖动是否被旧回调拉回。中央数字约 10 Hz 更新是预期行为，不应影响摇杆移动。
2. **连接 BLE 作对比。** 关闭 SIM，连接当前使用的 WL1 蓝牙模块，启用控制后重复相同拖动。分别记录“摇杆画面是否卡顿”和“小车动作是否滞后”。若 SIM 画面顺畅而连接后仍有动作延迟，需要继续检查真实链路耗时；TX 成功仅表示微信写入回调成功，不表示车端已经执行。
3. **检查双指松手。** 左右各按一根手指，先松左手，再反向测试先松右手。左手松开应只归零速度和转向；右手松开应保持最新腿高并归零横滚；另一根摇杆继续有效。再向同一杆增加一根手指，确认额外手指不会接管或提前释放原操作。
4. **检查操作中断。** 拖动期间切换页签、退到后台、再回前台，以及改变屏幕方向或窗口尺寸。确认旧摇杆不悬停、不被迟到事件重新拖动，布局重新测量后触点位置正确；回前台不会自动恢复运动。按页面状态重新连接、启用后，再确认新手势可正常开始。
5. **检查日志和复制。** 在遥控页操作一段时间后进入日志页，确认仍能看到最近收发记录；复制应包含最新缓存记录，不依赖列表是否已经刷新。清空后再次复制应为空，继续产生新记录后应只出现清空之后的内容。
